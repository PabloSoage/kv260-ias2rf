# Symbol libraries

*Updated: 21 September 2026*

A symbol whose pins are all `unspecified` makes ERC blind. That is exactly what produced the 48
uninterpretable `pin_to_pin` conflicts in the Rev01 work
([AUDIT_Rev01.md](AUDIT_Rev01.md) §2.2), and it is why this work exists: **every pin the design
uses has to carry a real electrical type**, or the verification story is theatre.

## 1. KiCad official libraries — used as-is

Not rebuilt. They ship with KiCad 10, are maintained, and copying them into a project library would
only create a second version to drift.

| Part | Library | Notes |
|---|---|---|
| **XC7A50T-FTG256** | `FPGA_Xilinx_Artix7` | The front-end FPGA. 256 pins, 4 units, 188 bidirectional + 68 `power_in`. Exactly the package AERIS-10 uses |
| **AD9708AR** | `Video` | Radar DAC. Exact part-number match |
| **ADF4351** | `RF` | SDR synthesiser for the front-end board |

That the hardest symbol in the design — a 256-ball BGA — was already available and correctly typed
was the single biggest saving in this phase.

## 3. Where the data comes from

analog.com would not serve its PDFs from this machine throughout this work — repeated 60 s
timeouts, and the mirrors return 403 and 410. Two other sources filled the gap.

### 3.1 Manufacturer datasheets, read locally

The AERIS-10 repository carries a component folder,
`7_Components Datasheets and Application notes/`, which turned out to hold the PDFs. Four symbols
were built from them:

| Symbol | Datasheet | Table used |
|---|---|---|
| `AD9484BCPZ-500` | `AD9484/AD9484.pdf` Rev. A | Table 7, Pin Function Descriptions |
| `AD8352ACPZ` | `AD9484/ad8352.pdf` Rev. C | Table 4, Pin Function Descriptions |
| `M3SWA2-34DR` | `M3SWA2-34DR+.pdf` | Functional diagram + DC Electrical Specifications |
| `LTC5552` | `LTC5552f.pdf` | Pin Configuration + Pin Functions |

### 3.2 The AERIS-10 Eagle library, for the rest

Eagle records a direction per pin, which maps cleanly onto what KiCad needs:

```
in  -> input     out -> output    io  -> bidirectional    pwr -> power_in
sup -> power_out pas -> passive   oc  -> open_collector   hiz -> tri_state
nc  -> no_connect
```

Those boards were fabricated and measured, so a wrong pinout would have shown up as a dead board.
It is good evidence, but **second-hand**, and every symbol carries a `SymbolSource` property saying
which route it came by.

### 3.3 The two sources agree

Worth recording, because it validates both. The `AD9484BCPZ-500` symbol was first built from Eagle
and then rebuilt from the datasheet. Comparing them:

- **57 pins on both sides**, pads 0 to 56, none missing, none duplicated
- 56 pads present in both
- 22 "name differences", **all of them Eagle's uniquifying suffixes** — `AVDD_3` against `AVDD`,
  `DNC_2` against `DNC`, and so on, because Eagle requires distinct pin names within a symbol

So the pinouts match exactly. That is mutual confirmation: AERIS's library is right, and the
datasheet reading is right.

## 4. `[?]` What is still not done

**`AD9523BCPZ` is untyped — 73 pins, all `passive`.** The Eagle symbol it came from was drawn
without typing its pins, so there was nothing to convert, and the AERIS folder holds no datasheet
for it. **It gives ERC no more than an untyped symbol would.** It is an AERIS-10 clock generator
rather than a part of this adapter, so the priority is low, but it is not done and the pin count
should not be read as implying otherwise.

**`AD9253` and `AD9767` have no symbols at all.** `_work/pinouts.txt` holds EasyEDA pin names for
both, but with `Dir = ?` throughout — names without types, which is the thing this exercise exists
to avoid. Neither datasheet is available locally.

`ADAR1000ACCZN` and `ADF4382A` remain Eagle-derived. Their types are plausible and complete, and
both are AERIS-10 parts rather than ours, so they are usable as-is; a spot-check against the
datasheets in the AERIS folder would settle them if they ever matter.

## 5. A design error this work uncovered

Retyping the `M3SWA2-34DR` from its datasheet showed that **blocker B-03 had been closed wrongly**.
It had been closed on a web search snippet reporting *"supply voltage requirement is 3.3V ~ 3.6V"*,
and the charge-pump inverter had been struck from the power tree on that basis.

The datasheet requires **VDD +3.3 V *and* VEE −3.3 V**. What is positive is the *control logic*,
which is not the same claim. The rail is back; see
[BLOCKERS_AND_RISKS.md](BLOCKERS_AND_RISKS.md) B-03.

**The symbol work paid for itself on that alone.** Fabricating the earlier power tree would have
left four RF switches dead and cost a board spin to find out why.

By KiCad, not by inspection:

```
kicad-cli sch erc          project ERC unchanged after registering the library
```

Eagle-against-datasheet comparison of §3.3.
